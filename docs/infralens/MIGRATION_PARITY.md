## Réserve connue (§21) — pré-existante, pas causée par la migration

**Les messages d'erreur conçus pour l'utilisateur (`userMessage` dans
`src/infralens/lib/security/errors.ts`) n'atteignent pas l'UI en mode
production.** Confirmé manuellement : soumettre `localhost` ou un domaine
inexistant est bien **bloqué** (0ms, zéro appel réseau, résultat "Unavailable",
grade E/0), mais le message affiché est le texte générique de redaction de
Next.js ("_An error occurred in the Server Components render. The specific
message is omitted in production builds..._") au lieu du message prévu
("_This target cannot be analyzed — it resolves to a non-public address._",
"_This domain could not be resolved._", etc.).

**Cause** : Next.js redacte automatiquement tout `Error` lancé depuis une
Server Action en mode `next start` (production), quel que soit son type —
comportement du framework, pas un bug introduit par la migration.

**Pourquoi ni la baseline source ni les tests migrés ne l'avaient détecté** :
le `playwright.config.ts` source démarre son `webServer` avec `pnpm dev`
(développement — pas de redaction), jamais `pnpm start`. Le produit
standalone tournait donc bien en production sur `infralens.dev` avec ce même
trou, jamais couvert par un test automatisé.

**Impact** : sécurité intacte (le blocage tient, aucune fuite), UX dégradée
(message générique au lieu du message clair conçu pour ça). N'a pas été
corrigé dans cette migration — signalé pour décision séparée plutôt que
corrigé silencieusement, conformément au principe "copier d'abord, ne pas
profiter de la migration pour changer le comportement" (§0 du plan).

## Ce qui a volontairement disparu

Uniquement la PWA InfraLens autonome (service worker, manifest, offline page,
install prompt, `basePath`, `INFRALENS_ORIGIN`, proxy multi-zone) —
conforme à la liste §51 du plan. InfraLens tourne désormais sous la PWA
globale de Randy Code.

## Limite déjà documentée, pas un écart de cette migration

L'historique localStorage de l'ancien domaine `infralens.dev` (production)
ne peut pas être lu automatiquement depuis `randy-code.dev` une fois en
ligne — origins différentes. Comportement attendu, déjà documenté au plan
§49 ; non applicable en local où les deux tournaient sur le même
`localhost:3000` (d'où les entrées d'historique visibles pendant les tests
manuels ci-dessus).
